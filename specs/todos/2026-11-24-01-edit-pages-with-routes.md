# Editing an entity happens in a modal, with no URL, and the forms have outgrown it

## Problem

Every create/edit form in the admin UI is a `Dialog` opened from local `useState`. The forms
have grown past what a modal holds: the grant definition dialog scrolls inside a fixed
height with the Save button floating over the "Priority" help text, the server group dialog
stacks three checkbox lists (servers, access approvers, query approvers) in one scroll box,
and the edit user dialog mixes roles, groups and two nested `AlertDialog`s. Nothing has a
URL, so an edit cannot be linked, bookmarked, reloaded or reached with the back button, and
an E2E test has to click through the list to open it.

Where the modals are today (state hook, then dialog component):

| Entity | List route | Modal |
|---|---|---|
| User | `front/src/routes/_authenticated/users/index.tsx` | `editUser` :77, `EditUserDialog` :516, `CreateUserDialog` :442 |
| User group | `user-groups/index.tsx` | `editing` :55, `GroupDialog` :204 |
| Server | `servers/index.tsx` | `editDb` :285, `renameDb` :284, `approversDb` :283 (`EditServerApproversDialog` :684), `editSshServer` :282, `detailDb` :281 (`DatabaseDetailsDialog` :1388), `CreateDatabaseDialog` :899 |
| Server group | `server-groups/index.tsx` | `editing` :56, `ServerGroupDialog` :219 |
| Grant definition | `grant-definitions/index.tsx` | `editing` :133, `DefinitionDialog` :488 |
| Grant | `grants/index.tsx` | `AssignGrantDialog` :434 |
| Grant request | `grant-requests/index.tsx` | `CreateRequestDialog` :348 |
| API key | `api-keys/index.tsx` | `CreateKeyDialog` :328 |
| Global parameter | `settings/index.tsx` | `editTarget` :752, inline dialog :843 |

`connections/$uid.tsx` and `queries/$uid.tsx` already show the target pattern for detail
pages (TanStack Router file routes).

## Proposal

Rule: **a form that creates or edits an entity is a page with its own route.** A dialog
stays only for a confirmation (delete, revoke, deactivate, deny, reset password, "you are
demoting yourself") or for a one-shot reveal (the new API key secret in `ShowKeyDialog`).

1. Routes, as TanStack file routes under `front/src/routes/_authenticated/` (the route tree
   `routeTree.gen.ts` is regenerated by the Vite plugin):
   - `users/new.tsx`, `users/$uid.tsx`
   - `user-groups/new.tsx`, `user-groups/$uid.tsx`
   - `servers/new.tsx`, `servers/$uid.tsx`: one page holding what is split today across
     details, edit, rename, approvers and the SSH tunnel edit. Rename keeps its own warning
     (CLAUDE.md: "the name in its own dialog, for its own warning"), as a section or a
     confirmation on save, not a separate modal form.
   - `server-groups/new.tsx`, `server-groups/$uid.tsx`
   - `grant-definitions/new.tsx`, `grant-definitions/$uid.tsx`
   - `grants/new.tsx` (assign), `grant-requests/new.tsx` (request access), `api-keys/new.tsx`
     (create; on success it navigates back to the list and the list shows `ShowKeyDialog`)
   - `settings/parameters/$key.tsx` for a global parameter
2. Each page loads the entity by uid with the existing React Query hooks, shows a loading
   state and a 404 state ("not found or archived" for a definition), and has Save and Cancel
   in a sticky footer. Save navigates back to the list; Cancel and the back button return
   without saving. The list's "Edit" action becomes a `<Link>`; the row name links too.
3. Move each `*Dialog` form body into a page component (e.g.
   `front/src/components/<entity>/<Entity>Form.tsx`) shared by `new` and `$uid`, dropping the
   `Dialog`/`DialogContent` wrapper and the `editing` state in the list. No behaviour change
   in the form itself: same fields, same validation, same API calls, same audit-relevant
   "send only what moved" logic on servers.
4. Grant definitions are immutably versioned: `$uid` resolves to the live row of the
   lineage. Saving creates a successor with a new uid, so the page redirects to the list, not
   to the old uid.
5. Keep every existing `data-testid` on the fields; rename the container testids from
   `*-dialog` to `*-page` (`edit-user-page`, `definition-page`, …) and update the E2E specs.
6. Layout: forms get the page width, long checkbox lists (servers, members, approvers) get a
   search filter and their own height instead of one shared scroll box.

## Tests

- E2E (`front/e2e/users.spec.ts`, `user-groups.spec.ts`, `servers.spec.ts`,
  `server-groups.spec.ts`, `grant-definitions.spec.ts`, `grants.spec.ts`,
  `grant-requests.spec.ts`, `api-keys.spec.ts`, `settings.spec.ts`): each existing create/edit
  case goes through the page instead of the dialog and still passes.
- New E2E per entity: `page.goto('/<entity>/<uid>')` directly opens the filled form;
  reloading keeps it; the back button returns to the list without saving.
- New E2E negative cases: an unknown uid shows the not-found state, not a blank form; a
  viewer (non-admin) hitting an admin edit route gets the same access refusal as the list.
- New E2E: saving a grant definition lands on the list and the new version is listed, the old
  uid no longer resolves to an editable form.
- `bun run lint`, `bun run build` (type check) pass.

## To verify

- Which list pages the `viewer` role can see, and how the list routes refuse non-admins today
  (route `beforeLoad` or in-component check): the edit routes must refuse the same way.
- Whether `DatabaseDetailsDialog` (servers :1388) is reachable by non-admins (the connection
  URL card in it is for connectors): if so, `servers/$uid` needs a read-only view for them.
- Whether `grant-definitions` has a "view archived version" path that would also need a route.

## Open questions

- **Create forms too, or edit only?** Recommended: both. The create and edit forms are the
  same component in most files (`GroupDialog`, `ServerGroupDialog`, `DefinitionDialog`), and
  splitting them would leave half of each.
- **Small one-field forms (global parameter, request access, assign grant, create API key):
  page or keep the dialog?** Recommended: pages for consistency, since "anything we edit has
  a route" is the rule being set; the parameter edit is the only borderline one.
- **One `servers/$uid` page, or keep rename / approvers / SSH as separate routes
  (`servers/$uid/approvers`)?** Recommended: one page with sections, one Save per section
  where the API calls are separate today.
