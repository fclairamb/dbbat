# A 429 on the session check logs the user out; rate limiting must never destroy a valid session

## Problem

The auth bootstrap treats *any* failed `/auth/me` call as "this token is
invalid":

- `validateSession()` returns `false` whenever `response.error` is set,
  without looking at the status
  ([AuthContext.tsx:60](front/src/contexts/AuthContext.tsx:60)).
- `checkStoredAuth()` then calls `clearToken()` and wipes state + query cache
  ([AuthContext.tsx:98](front/src/contexts/AuthContext.tsx:98)–109), dropping
  the user on the login screen.

`GET /auth/me` is rate-limited — the schema declares a 429 `AuthRateLimited`
response ([schema.ts:3279](front/src/api/schema.ts:3279)). So a user who
merely hits the rate limit (e.g. several tabs booting at once, or someone
else hammering auth endpoints from the same source) gets their perfectly
valid session token deleted and is forcibly logged out. The 429 says "try
again later"; the app answers "your session is gone".

The response middleware itself is fine — it only redirects on 401
([client.ts:36](front/src/api/client.ts:36)); the destructive path is the
bootstrap's error-blind `valid = false` branch.

Adjacent, same file: the login handler extracts `errorData?.code` and throws
"Login failed" otherwise ([AuthContext.tsx:124](front/src/contexts/AuthContext.tsx:124)–130),
so a 429 on login shows a generic failure instead of "too many attempts, try
again shortly".

## Proposal

Distinguish "the token is definitively invalid" from "the check could not be
performed":

1. In `validateSession()`, capture `response.response.status`
   (openapi-fetch exposes the raw `Response`). Only report the session as
   invalid on **401**. On **429** — and arguably any 5xx / network error —
   keep the stored token, leave `isAuthenticated` as-is, and surface a
   non-destructive signal instead.
2. In `checkStoredAuth()`, only `clearToken()` + `queryClient.clear()` when
   the session is *definitively* invalid. For the rate-limited case, finish
   loading (`isLoading: false`) without clearing, and show a message — e.g.
   an inline banner/toast: "Too many requests — please retry in a moment."
   Honor `Retry-After` when present by scheduling one automatic re-validate.
3. Login path: map a 429 from `POST /auth/login` to a clear "over the limit"
   message on the form instead of the generic "Login failed"
   ([login.tsx](front/src/routes/login.tsx) consumes the thrown code).
4. Add a `data-testid` to the new message per front/CLAUDE.md conventions,
   and cover the behavior: an e2e or component test that a 429 on
   `/auth/me` leaves `dbbat_session_token` in localStorage and does not
   redirect to `/app/login`.

Out of scope: changing backend rate limits, and generic 429 toasts on
non-auth endpoints (those already fail per-query via TanStack Query without
logging anyone out — a global retry/backoff policy could be a separate todo).
